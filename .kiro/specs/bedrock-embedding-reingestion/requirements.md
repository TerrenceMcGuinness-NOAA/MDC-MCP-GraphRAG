# Requirements Document

## Introduction

This specification defines the requirements for executing the Bedrock embedding re-ingestion pipeline against the existing AWS infrastructure. Phase 49 built the complete multi-model embedding infrastructure (embedding registry, Bedrock provider, model-aware ingestion scripts, OpenSearch index creation, hybrid search, Matryoshka queries, benchmarking, and drift detection). Phase 50/50b completed the S3 migration, populating 5 OpenSearch indices with 85,921 documents using mpnet768 embeddings. This spec covers the execution phase: creating titan1024 OpenSearch indices, re-ingesting all 5 collections with Bedrock Titan embeddings, benchmarking titan1024 vs mpnet768, testing Nova Matryoshka queries, establishing drift baselines, and optionally building the SageMaker container for offloaded processing jobs.

## Glossary

- **Titan1024_Model**: The Amazon Titan Embed Text V2 model (`amazon.titan-embed-text-v2:0`) accessed via AWS Bedrock, producing 1024-dimensional embeddings. Registered in the Embedding_Model_Registry as `titan1024`.
- **Nova_Model**: The Amazon Nova Multimodal Embed V1 model (`amazon.nova-multimodal-embed-v1`) accessed via AWS Bedrock, supporting Matryoshka embeddings at 256, 512, 1024, and 3072 dimensions. Registered as `nova256`, `nova512`, `nova1024`, `nova3072`.
- **Mpnet768_Model**: The existing local `all-mpnet-base-v2` model producing 768-dimensional embeddings. The current baseline model with 5 populated OpenSearch indices.
- **OpenSearch_Index**: A k-NN enabled index in the AWS OpenSearch cluster (`vpc-mdc-mcp-rag-search-5o72hixfx3rryikwb7l5px5sgq.us-east-1.es.amazonaws.com`) with HNSW vector mappings and BM25 text fields.
- **Re_Ingestion**: The process of running existing ingestion scripts against existing source data with a different Model_Profile, producing new embeddings in new model-aware OpenSearch indices.
- **Benchmark_Report**: A structured comparison of retrieval quality metrics (precision@k, recall@k, MRR, nDCG) across model/search-mode combinations, generated by `benchmark_runner.py`.
- **Drift_Baseline**: The initial drift detection report for a collection, establishing mean and minimum cosine similarity scores against which future drift is measured.
- **Ground_Truth_File**: A JSON file mapping test queries to expected relevant document IDs, used by the Benchmark_Runner to compute retrieval quality metrics.
- **SageMaker_Container**: A Docker image built from `Dockerfile.sagemaker` containing all ingestion scripts and dependencies, pushed to ECR for use in SageMaker Processing Jobs.
- **Matryoshka_Query**: A query that truncates stored high-dimensional embeddings to a lower-dimensional prefix at query time, enabling cost/quality tradeoffs without re-indexing. Implemented in `MatryoshkaQuery.js`.
- **Collection_Domain**: One of the 5 content domains: `code-with-context`, `global-workflow-docs`, `jjobs`, `community-summaries`, `ee2-standards`.

## Requirements

### Requirement 1: Create Titan1024 OpenSearch Indices

**User Story:** As an operator, I want to create 5 new OpenSearch indices configured for 1024-dimensional Titan embeddings, so that the re-ingestion pipeline has target indices to write to.

#### Acceptance Criteria

1. WHEN `create-opensearch-indices.js --model titan1024` is executed, THE Index_Creator SHALL create 5 new OpenSearch indices named `mdc-code-context-titan1024`, `mdc-workflow-docs-titan1024`, `mdc-jjobs-titan1024`, `mdc-community-summaries-titan1024`, and `mdc-ee2-standards-titan1024`.
2. THE Index_Creator SHALL configure each titan1024 index with `knn_vector` dimension set to 1024, HNSW engine with `ef_construction: 512` and `m: 16`, and `cosinesimil` space type.
3. THE Index_Creator SHALL configure each titan1024 index with a `content` field of type `text` for BM25 keyword search.
4. IF an index already exists, THEN THE Index_Creator SHALL skip that index and log a message indicating it was skipped.
5. WHEN all 5 indices are created, THE operator SHALL verify the indices exist by querying the OpenSearch cluster's `_cat/indices` endpoint and confirming 10 total indices (5 mpnet768 + 5 titan1024).

### Requirement 2: Bedrock Titan Re-Ingestion of Code Collection

**User Story:** As an operator, I want to re-ingest the code-with-context collection using Titan1024 embeddings, so that I have a Bedrock-embedded vector space for the largest collection (60,576 documents).

#### Acceptance Criteria

1. WHEN `ingest_code_v8.py --model titan1024 --backend aws` is executed, THE Ingestion_Script SHALL generate embeddings using the Bedrock Titan Embed Text V2 API for all code documents.
2. THE Ingestion_Script SHALL write documents to the `mdc-code-context-titan1024` OpenSearch index via the model-aware collection naming convention.
3. WHEN the ingestion completes, THE operator SHALL verify the document count in `mdc-code-context-titan1024` matches the mpnet768 baseline count of approximately 60,576 documents (within 1% tolerance).
4. IF the Bedrock API returns a throttling error, THEN THE Ingestion_Script SHALL retry with exponential backoff as implemented in the BedrockProvider.
5. THE Ingestion_Script SHALL log progress at regular intervals showing documents processed and estimated time remaining.

### Requirement 3: Bedrock Titan Re-Ingestion of Documentation Collection

**User Story:** As an operator, I want to re-ingest the global-workflow-docs collection using Titan1024 embeddings, so that I have Bedrock-embedded documentation for comparative analysis.

#### Acceptance Criteria

1. WHEN `ingest_documentation_v8.py --model titan1024 --backend aws` is executed, THE Ingestion_Script SHALL generate embeddings using the Bedrock Titan Embed Text V2 API for all documentation chunks.
2. THE Ingestion_Script SHALL write documents to the `mdc-workflow-docs-titan1024` OpenSearch index.
3. WHEN the ingestion completes, THE operator SHALL verify the document count in `mdc-workflow-docs-titan1024` matches the mpnet768 baseline count of approximately 22,498 documents (within 1% tolerance).

### Requirement 4: Bedrock Titan Re-Ingestion of Remaining Collections

**User Story:** As an operator, I want to re-ingest the jjobs, community-summaries, and ee2-standards collections using Titan1024 embeddings, so that all 5 content domains have parallel Bedrock vector spaces.

#### Acceptance Criteria

1. WHEN `ingest_jjobs_v8.py --model titan1024 --backend aws` is executed, THE Ingestion_Script SHALL write Titan1024 embeddings to the `mdc-jjobs-titan1024` OpenSearch index, producing approximately 700 documents.
2. WHEN `ingest_shell_graph_v8.py --model titan1024 --backend aws` is executed, THE Ingestion_Script SHALL write Titan1024 embeddings to the `mdc-community-summaries-titan1024` OpenSearch index, producing approximately 2,113 documents.
3. WHEN `ingest_ee2_v7.py --model titan1024 --backend aws` is executed, THE Ingestion_Script SHALL write Titan1024 embeddings to the `mdc-ee2-standards-titan1024` OpenSearch index, producing approximately 34 documents.
4. WHEN all 5 re-ingestion runs complete, THE operator SHALL verify total titan1024 document count across all 5 indices is approximately 85,921 (matching the mpnet768 total within 1% tolerance).

### Requirement 5: Ground Truth File Creation

**User Story:** As a researcher, I want a ground truth file mapping test queries to expected relevant documents, so that the benchmark runner can compute meaningful retrieval quality metrics.

#### Acceptance Criteria

1. THE operator SHALL create a Ground_Truth_File containing at least 20 test queries spanning all 5 Collection_Domains.
2. THE Ground_Truth_File SHALL map each query to a list of expected relevant document IDs that exist in both the mpnet768 and titan1024 indices.
3. THE Ground_Truth_File SHALL include queries of varying complexity: simple keyword lookups, multi-concept queries, code identifier queries, and natural language questions.
4. THE Ground_Truth_File SHALL be stored at `mcp_server_node/scripts/config/benchmark_ground_truth.json` in the format expected by `benchmark_runner.py`.

### Requirement 6: Benchmark Titan1024 vs Mpnet768

**User Story:** As a researcher, I want to benchmark retrieval quality of Titan1024 against Mpnet768 across all collections, so that I can quantify the quality difference between local and Bedrock embeddings.

#### Acceptance Criteria

1. WHEN `benchmark_runner.py` is executed with the Ground_Truth_File and both mpnet768 and titan1024 vector spaces, THE Benchmark_Runner SHALL compute precision@5, precision@10, recall@5, recall@10, MRR, and nDCG for each model/search-mode combination.
2. THE Benchmark_Runner SHALL evaluate both `vector` and `hybrid` search modes for each model, producing at least 4 result rows (mpnet768-vector, mpnet768-hybrid, titan1024-vector, titan1024-hybrid).
3. THE Benchmark_Runner SHALL generate a markdown comparison table and upload the full report to S3.
4. THE Benchmark_Report SHALL include query latency measurements (p50, p95, p99) for each model/search-mode combination.

### Requirement 7: Matryoshka Query Testing with Nova Embeddings

**User Story:** As a researcher, I want to test Matryoshka dimension truncation with Nova embeddings at multiple dimension levels, so that I can evaluate the cost/quality tradeoff of adaptive dimension search.

#### Acceptance Criteria

1. THE operator SHALL create at least one Nova OpenSearch index (e.g., `mdc-workflow-docs-nova1024`) and ingest a representative subset of documents (at least 100) using Nova 1024-dim embeddings.
2. WHEN a MatryoshkaQuery is executed with `dimensions: 256` against the nova1024 index, THE MatryoshkaQuery SHALL truncate the query vector to 256 dimensions and return results using script_score cosine similarity on the truncated prefix.
3. WHEN a MatryoshkaQuery is executed with `dimensions: 512` against the nova1024 index, THE MatryoshkaQuery SHALL return results using the 512-dimension prefix.
4. THE operator SHALL compare retrieval quality at dimensions 256, 512, and 1024 for the same set of test queries and document the quality/latency tradeoff.

### Requirement 8: Drift Detection Baseline

**User Story:** As an operator, I want to establish drift detection baselines for the titan1024 collections, so that future re-embeddings can be compared against a known-good state.

#### Acceptance Criteria

1. WHEN `drift_detector.py <collection> --backend aws --sample-size 100` is executed against each titan1024 collection, THE Drift_Detector SHALL sample 100 documents, re-embed them using the Bedrock Titan API, and compute cosine similarity between stored and fresh embeddings.
2. THE Drift_Detector SHALL report mean similarity of at least 0.99 for freshly ingested collections (no drift expected immediately after ingestion).
3. THE Drift_Detector SHALL upload each Drift_Baseline report to S3 at `s3://mdc-mcp-rag-drift-reports/drift-reports/<collection>/<timestamp>.json`.
4. IF the Drift_Detector reports mean similarity below 0.95, THEN THE operator SHALL investigate whether the Bedrock model version has changed or source data has been modified.

### Requirement 9: SageMaker Container Build and Test (Optional)

**User Story:** As an operator, I want to build the SageMaker Docker container and verify it can run a test processing job, so that future large-scale re-ingestion can be offloaded from the development EC2 instance.

#### Acceptance Criteria

1. THE operator SHALL build the SageMaker Docker image from `Dockerfile.sagemaker` and tag it as `mdc-mcp-rag-ingestion:latest`.
2. THE operator SHALL push the Docker image to the ECR repository in the same AWS account and region.
3. WHEN `sagemaker_launcher.py ingest_ee2_v7.py --model titan1024 --backend aws --dry-run` is executed, THE SageMaker_Launcher SHALL estimate the cost without submitting a job.
4. WHERE the `SAGEMAKER_ROLE_ARN` environment variable is set, THE operator SHALL submit a test SageMaker Processing Job using the smallest collection (`ee2-standards`, 34 documents) and verify it completes successfully.
5. IF `SAGEMAKER_ROLE_ARN` is not set, THEN THE operator SHALL document the missing IAM role and skip the live job submission.

### Requirement 10: Hybrid Search Validation

**User Story:** As a researcher, I want to validate that hybrid search (BM25 + vector + RRF) works correctly with titan1024 embeddings, so that I can confirm the full search pipeline is functional with Bedrock embeddings.

#### Acceptance Criteria

1. WHEN a hybrid search query is executed against a titan1024 index using the HybridSearchBuilder, THE Search_Builder SHALL combine BM25 keyword matching on the `content` field with k-NN vector search on the 1024-dim `embedding` field.
2. WHEN the query contains code identifiers (camelCase, snake_case, dot.notation, file paths), THE Search_Builder SHALL auto-boost the BM25 weight by 2x.
3. THE operator SHALL execute at least 5 hybrid search queries against titan1024 indices and verify that results contain both keyword-matched and semantically-matched documents.
4. THE operator SHALL compare hybrid search results between mpnet768 and titan1024 for the same queries and document any significant ranking differences.
