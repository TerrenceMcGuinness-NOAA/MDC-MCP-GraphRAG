# Requirements Document

## Introduction

This specification defines the requirements for restructuring the ingestion pipeline of the GraphRAG MCP server system. The current pipeline hardcodes a single embedding model (`all-mpnet-base-v2`, 768 dimensions), duplicates backend-routing boilerplate across 7+ scripts, provides no idempotency guarantees, and cannot maintain parallel vector spaces for comparative analysis. This refactor introduces multi-model embedding support, model-aware collection naming, centralized backend routing, idempotent re-runs, and dead code archival — enabling the team to run comparative analysis across disparate feature spaces (e.g., MPNet 768-dim vs. Bedrock Titan 1024-dim).

## Glossary

- **Ingestion_Pipeline**: The set of Python scripts under `mcp_server_node/scripts/` that parse, chunk, embed, and store documentation, code, and graph data into vector and graph databases.
- **Embedding_Model_Registry**: A centralized configuration component that defines available embedding models, their providers, dimensions, and invocation methods.
- **Model_Profile**: A named entry in the Embedding_Model_Registry specifying a model identifier, provider (local or Bedrock), dimension count, and any provider-specific parameters.
- **Vector_Space**: A single collection (ChromaDB) or index (OpenSearch) containing embeddings generated by one specific Embedding Model. Each Vector_Space is scoped to one Model_Profile and one content domain.
- **Model_Aware_Name**: A collection or index name that encodes the embedding model used, following the pattern `{content-domain}-{version}-{model-short-name}` (e.g., `code-with-context-v8-0-0-mpnet768`, `code-with-context-v8-0-0-titan1024`).
- **Backend_Router**: The centralized component in `ingestion_base.py` that resolves the `DB_BACKEND` environment variable or `--backend` CLI flag and returns the appropriate vector and graph database clients.
- **Idempotent_Ingestion**: An ingestion run that, when executed multiple times on the same input data, produces an identical database state with no duplicate documents, no orphaned records, and deterministic document IDs.
- **Deterministic_ID**: A document identifier derived from a hash of the content, source path, and model profile — ensuring the same input always produces the same ID.
- **Bedrock_Provider**: The AWS Bedrock API service used to generate embeddings via models such as Amazon Titan Embeddings V2 (1024-dim) or Cohere Embed (1024-dim).
- **Local_Provider**: The `sentence-transformers` library used to generate embeddings locally on CPU (e.g., `all-mpnet-base-v2`, 768-dim).
- **Comparative_Query**: A query executed against multiple Vector_Spaces containing the same content domain but different embedding models, returning ranked results from each for side-by-side comparison.
- **Node_Adapter_Layer**: The existing `VectorDatabaseAdapter` and `GraphDatabaseAdapter` interfaces in `mcp_server_node/src/data/adapters/` that abstract database backends for the 51 MCP tools.
- **Dead_Code**: The `mcp_server_python/` directory containing an unused Python MCP server prototype that has been superseded by the Node.js MCP server.

## Requirements

### Requirement 1: Embedding Model Registry

**User Story:** As a developer, I want a centralized registry of embedding models, so that I can add new models without modifying individual ingestion scripts.

#### Acceptance Criteria

1. THE Embedding_Model_Registry SHALL define each Model_Profile with a unique short name, provider type (local or bedrock), model identifier, embedding dimension count, and provider-specific parameters.
2. THE Embedding_Model_Registry SHALL include a Model_Profile for `all-mpnet-base-v2` (local provider, 768 dimensions) as the default profile.
3. THE Embedding_Model_Registry SHALL include a Model_Profile for Amazon Titan Embeddings V2 (bedrock provider, 1024 dimensions).
4. WHEN a new Model_Profile is added to the Embedding_Model_Registry, THE Ingestion_Pipeline SHALL support the new model without changes to individual ingestion scripts.
5. THE Embedding_Model_Registry SHALL be defined in a single configuration file or module under `mcp_server_node/scripts/`.

### Requirement 2: Embedding Provider Abstraction

**User Story:** As a developer, I want a unified interface for generating embeddings regardless of provider, so that ingestion scripts do not need to know whether embeddings come from a local model or Bedrock.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL provide an embedding provider interface that accepts text input and returns a vector of the dimension specified by the active Model_Profile.
2. WHEN the active Model_Profile specifies the local provider, THE Ingestion_Pipeline SHALL generate embeddings using the `sentence-transformers` library.
3. WHEN the active Model_Profile specifies the bedrock provider, THE Ingestion_Pipeline SHALL generate embeddings using the AWS Bedrock API via `boto3`.
4. IF the Bedrock API returns an error, THEN THE Ingestion_Pipeline SHALL log the error with the model identifier and input text length, and raise an exception.
5. IF the local model file is not found in the cache, THEN THE Ingestion_Pipeline SHALL download the model to `$CACHE_ROOT/huggingface` before generating embeddings.

### Requirement 3: Model-Aware Collection and Index Naming

**User Story:** As a developer, I want collection and index names to encode the embedding model used, so that I can identify which model generated the embeddings in a given vector space.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL generate Model_Aware_Names for all new collections and indices by appending a model short name suffix to the existing collection name pattern.
2. WHEN the active Model_Profile is `all-mpnet-base-v2`, THE Ingestion_Pipeline SHALL append `-mpnet768` to collection and index names.
3. WHEN the active Model_Profile is Amazon Titan Embeddings V2, THE Ingestion_Pipeline SHALL append `-titan1024` to collection and index names.
4. THE Backend_Router SHALL maintain a mapping from Model_Aware_Names to OpenSearch index names that preserves the model suffix convention.
5. THE Ingestion_Pipeline SHALL retain the ability to read from legacy collection names (without model suffix) for backward compatibility during migration.

### Requirement 4: Disparate Vector Spaces

**User Story:** As a researcher, I want to maintain separate vector spaces for different embedding models over the same content, so that I can compare retrieval quality across feature spaces.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL create a separate Vector_Space for each combination of content domain and Model_Profile.
2. WHEN an ingestion script is run with Model_Profile A and then re-run with Model_Profile B, THE Ingestion_Pipeline SHALL write to two distinct Vector_Spaces without overwriting or mixing embeddings.
3. THE Ingestion_Pipeline SHALL support specifying the target Model_Profile via a `--model` CLI argument on any ingestion script.
4. WHILE multiple Vector_Spaces exist for the same content domain, THE Ingestion_Pipeline SHALL keep each Vector_Space independently queryable.

### Requirement 5: Comparative Analysis Support

**User Story:** As a researcher, I want to query the same content across different vector spaces and compare results side by side, so that I can evaluate which embedding model produces better retrieval for specific query types.

#### Acceptance Criteria

1. THE Node_Adapter_Layer SHALL support Comparative_Queries that execute a single query text against multiple Vector_Spaces and return ranked results from each.
2. WHEN a Comparative_Query is executed, THE Node_Adapter_Layer SHALL embed the query text using each target Vector_Space's corresponding Model_Profile.
3. THE Node_Adapter_Layer SHALL return Comparative_Query results grouped by Model_Profile, each group containing the same result structure as a standard vector query.
4. THE Node_Adapter_Layer SHALL preserve the existing single-model query interface for all 51 MCP tools without modification.

### Requirement 6: Centralized Backend Routing

**User Story:** As a developer, I want backend routing logic centralized in one place, so that I do not have to maintain identical boilerplate across 14+ ingestion scripts.

#### Acceptance Criteria

1. THE Backend_Router SHALL parse the `--backend` CLI flag and `DB_BACKEND` environment variable in a single location within `ingestion_base.py`.
2. WHEN an ingestion script initializes, THE Backend_Router SHALL provide the appropriate vector client and graph driver based on the resolved backend setting.
3. THE Ingestion_Pipeline SHALL remove all inline `--backend` parsing boilerplate from individual ingestion scripts (`ingest_code_v8.py`, `ingest_fortran_graph.py`, `ingest_shell_graph_v8.py`, `ingest_documentation_v8.py`, `ingest_jjobs_v8.py`, `ingest_cross_language_bridges.py`, `ingest_env_variables.py`).
4. WHEN the `--backend` flag is not provided and `DB_BACKEND` is not set, THE Backend_Router SHALL default to the `legacy` backend.
5. IF an unknown backend value is provided, THEN THE Backend_Router SHALL exit with a descriptive error message.

### Requirement 7: Idempotent Ingestion

**User Story:** As a developer, I want to re-run any ingestion script and get identical results, so that I can safely recover from partial failures and maintain consistent database state.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL generate Deterministic_IDs for each document by hashing the content, source path, chunk index, and active Model_Profile short name.
2. WHEN an ingestion script is run a second time on the same input data with the same Model_Profile, THE Ingestion_Pipeline SHALL produce a database state identical to the first run with zero duplicate documents.
3. WHEN an ingestion script is run after source content has changed, THE Ingestion_Pipeline SHALL update changed documents and remove documents whose source content no longer exists.
4. THE Ingestion_Pipeline SHALL use upsert semantics (insert-or-update) for all vector database writes.
5. THE Ingestion_Pipeline SHALL use MERGE semantics for all graph database writes to prevent duplicate nodes and relationships.
6. FOR ALL ingestion scripts, running the script N times on unchanged input SHALL produce the same document count as running the script once (idempotence property).

### Requirement 8: Model Selection CLI Interface

**User Story:** As a developer, I want a consistent CLI interface across all ingestion scripts for selecting the embedding model, so that I can switch models without remembering script-specific flags.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL accept a `--model` CLI argument on every ingestion script that performs vector embedding.
2. WHEN the `--model` argument is provided, THE Ingestion_Pipeline SHALL resolve the corresponding Model_Profile from the Embedding_Model_Registry.
3. WHEN the `--model` argument is omitted, THE Ingestion_Pipeline SHALL use the default Model_Profile (`all-mpnet-base-v2`).
4. IF the `--model` argument specifies a model not in the Embedding_Model_Registry, THEN THE Ingestion_Pipeline SHALL exit with an error listing available models.
5. THE Ingestion_Pipeline SHALL pass the resolved Model_Profile to the embedding provider and the collection naming function.

### Requirement 9: Dead Code Archival

**User Story:** As a developer, I want unused prototype code moved out of the active source tree, so that the repository is clean and new contributors are not confused by dead code.

#### Acceptance Criteria

1. THE Ingestion_Pipeline refactor SHALL move the `mcp_server_python/` directory to `archive/mcp_server_python/`.
2. WHEN the `mcp_server_python/` directory is archived, THE Ingestion_Pipeline refactor SHALL update `.gitmodules` if it references `mcp_server_python/`.
3. THE Ingestion_Pipeline refactor SHALL verify that no active script or configuration file imports from or references `mcp_server_python/`.

### Requirement 10: OpenSearch Index Dimension Compatibility

**User Story:** As a developer, I want OpenSearch indices configured with the correct vector dimensions for each embedding model, so that k-NN search works correctly across disparate vector spaces.

#### Acceptance Criteria

1. WHEN a new Vector_Space is created for a Model_Profile with N dimensions, THE Backend_Router SHALL create or verify an OpenSearch index with `knn_vector` mapping of N dimensions.
2. THE Backend_Router SHALL support indices with different dimension counts coexisting in the same OpenSearch domain.
3. IF a document with an embedding of dimension M is written to an index configured for dimension N where M does not equal N, THEN THE Backend_Router SHALL reject the write with a descriptive error.

### Requirement 11: Backward Compatibility

**User Story:** As a developer, I want the existing 85,995 documents across 6 collections to remain accessible during and after the refactor, so that the 51 MCP tools continue working without interruption.

#### Acceptance Criteria

1. WHILE the refactor is in progress, THE Node_Adapter_Layer SHALL continue to serve queries against existing legacy collections and indices.
2. THE Ingestion_Pipeline refactor SHALL preserve the existing `COLLECTION_TO_INDEX` mapping in `aws_backend.py` for legacy collection names.
3. WHEN a query targets a legacy collection name (without model suffix), THE Node_Adapter_Layer SHALL route the query to the existing index.
4. THE Ingestion_Pipeline refactor SHALL not modify the `VectorDatabaseAdapter` or `GraphDatabaseAdapter` interfaces in a way that breaks existing adapter implementations.

### Requirement 12: Bedrock Authentication and Configuration

**User Story:** As a developer, I want Bedrock API access configured through standard AWS credential chains, so that ingestion scripts can generate embeddings on AWS without hardcoded credentials.

#### Acceptance Criteria

1. WHEN the active Model_Profile specifies the bedrock provider, THE Ingestion_Pipeline SHALL authenticate using the default AWS credential chain (`boto3.Session()`).
2. THE Ingestion_Pipeline SHALL use the AWS region specified by `AWS_REGION` environment variable (default: `us-east-1`) for Bedrock API calls.
3. IF AWS credentials are not available when a bedrock Model_Profile is active, THEN THE Ingestion_Pipeline SHALL exit with a descriptive error indicating the required IAM permissions.

### Requirement 13: Ingestion Base Refactor

**User Story:** As a developer, I want `ingestion_base.py` to serve as the single entry point for all shared ingestion infrastructure, so that new scripts can be written with minimal boilerplate.

#### Acceptance Criteria

1. THE `ingestion_base.py` module SHALL export a `BaseIngester` class that provides backend routing, embedding generation, collection naming, and idempotent write methods.
2. WHEN a new ingestion script is created, THE script SHALL require only subclassing `BaseIngester` and implementing a content extraction method.
3. THE `ingestion_base.py` module SHALL remove the hardcoded `EMBEDDING_MODEL = "all-mpnet-base-v2"` constant and replace it with Model_Profile resolution from the Embedding_Model_Registry.
4. THE `ingestion_base.py` module SHALL consolidate the `ChromaDBClient.connect()` backend-routing logic and the `aws_backend.py` client factory into a unified `get_clients()` method.

### Requirement 14: Model-Aware Data Migration

**User Story:** As a developer, I want the migration script (`migrate-to-aws.js`) to support model-aware collection and index naming, so that I can migrate disparate vector spaces from ChromaDB to OpenSearch without losing model provenance.

#### Acceptance Criteria

1. THE migration script SHALL read the Model_Profile metadata from each ChromaDB collection to determine the embedding model and dimension count used.
2. WHEN exporting a ChromaDB collection, THE migration script SHALL include the Model_Profile short name in the S3 export key (e.g., `vectors/code-with-context-v8-0-0-mpnet768.json.gz`).
3. WHEN loading vectors into OpenSearch, THE migration script SHALL target the Model_Aware_Name index corresponding to the source collection's Model_Profile.
4. THE migration script SHALL support migrating multiple Vector_Spaces for the same content domain (e.g., both `-mpnet768` and `-titan1024` variants) in a single run.
5. THE migration script SHALL preserve the existing legacy collection → index mapping (`COLLECTION_TO_INDEX`) for backward compatibility with collections that predate model-aware naming.
6. THE migration script SHALL use S3 watermarks per collection-model combination for idempotent re-execution on failure.

### Requirement 15: Model-Aware OpenSearch Index Creation

**User Story:** As a developer, I want the index creation script (`create-opensearch-indices.js`) to create indices with the correct vector dimensions for each embedding model, so that k-NN search works correctly across disparate vector spaces.

#### Acceptance Criteria

1. THE index creation script SHALL accept a `--model` argument to specify which Model_Profile's indices to create.
2. WHEN `--model` is omitted, THE index creation script SHALL create indices for the default Model_Profile (`all-mpnet-base-v2`, 768 dimensions).
3. WHEN `--model all` is specified, THE index creation script SHALL create indices for every Model_Profile in the Embedding_Model_Registry.
4. THE index creation script SHALL set the `knn_vector` dimension in the index mapping to match the specified Model_Profile's embedding dimension count.
5. THE index creation script SHALL use Model_Aware_Names for all new indices (e.g., `mdc-code-context-mpnet768`, `mdc-code-context-titan1024`).
6. THE index creation script SHALL be idempotent — running it multiple times SHALL not fail or create duplicate indices.

### Requirement 16: Graph Migration Independence

**User Story:** As a developer, I want graph data migration (Neo4j → Neptune) to remain independent of the embedding model, so that graph structure is shared across all vector spaces.

#### Acceptance Criteria

1. THE migration script SHALL export and load graph data (Neo4j → S3 → Neptune) independently of any Model_Profile.
2. THE graph migration SHALL produce exactly one Neptune graph instance shared by all Vector_Spaces.
3. WHEN the migration script is run with a `--phase` argument targeting only vector phases (`export-vectors`, `load-vectors`), THE graph data SHALL remain untouched.
4. THE graph migration SHALL continue to use MERGE semantics to prevent duplicate nodes and relationships on re-execution.

### Requirement 17: Migration Verification for Multi-Model

**User Story:** As a developer, I want the verification script to validate count parity across all model-specific vector spaces, so that I can confirm every vector space was migrated completely.

#### Acceptance Criteria

1. THE verification script SHALL check count parity for every Model_Aware_Name index present in OpenSearch, not just the legacy 5-index mapping.
2. THE verification script SHALL report per-model, per-collection counts in its parity report.
3. THE verification script SHALL upload the parity report to S3 with a timestamp for audit trail.
4. THE verification script SHALL exit with a non-zero code if any model-specific index has a count mismatch.

### Requirement 18: Cross-Environment Migration Execution

**User Story:** As a developer, I want clear guidance on which migration phases run from which environment, so that I can execute the migration across two machines that have different network access.

#### Acceptance Criteria

1. THE migration script SHALL support running individual phases via `--phase <phase-name>` so that export and load phases can be executed from different machines.
2. THE export phases (`export-vectors`, `export-graph`) SHALL require only network access to the legacy databases (ChromaDB, Neo4j) and write access to the S3 staging bucket.
3. THE load phases (`load-vectors`, `load-graph`) SHALL require only network access to the AWS databases (OpenSearch, Neptune) and read access to the S3 staging bucket.
4. THE migration script SHALL document the recommended execution order: (a) run export phases from the legacy Parallel Works VM, (b) run load phases from the AWS EC2 instance, (c) run verify phase from the AWS EC2 instance.
5. THE S3 staging bucket (`mdc-mcp-rag-migration`) SHALL serve as the sole data handoff point between the two environments — no direct network connection between legacy databases and AWS databases is required.
6. THE migration script SHALL validate that required environment variables are set for the active phase and exit with a descriptive error if any are missing (e.g., `CHROMADB_URL` for export-vectors, `OPENSEARCH_ENDPOINT` for load-vectors).
7. THE verify phase SHALL be runnable from either environment, requiring only S3 read access and network access to the target databases being verified.

### Requirement 19: Migration Execution Order and Prerequisites

**User Story:** As a developer, I want a documented prerequisite chain for the migration, so that I know exactly what must be deployed before each step can run.

#### Acceptance Criteria

1. BEFORE running the migration, THE following AWS resources SHALL be deployed via `cdk deploy --all`: VPC, security groups, Neptune cluster, OpenSearch domain, S3 staging bucket, and EFS filesystem.
2. BEFORE running the load-vectors phase, THE OpenSearch indices SHALL be created via `create-opensearch-indices.js` with the correct k-NN vector dimensions for each target Model_Profile.
3. BEFORE running the load-graph phase, THE Neptune cluster SHALL be accessible via its bolt endpoint from the AWS EC2 instance.
4. THE migration script SHALL check for prerequisite completion (e.g., verify OpenSearch indices exist before bulk loading) and exit with a descriptive error if prerequisites are not met.
5. THE complete migration execution order SHALL be: (a) `cdk deploy --all`, (b) `create-opensearch-indices.js`, (c) `migrate-to-aws.js --phase export-vectors` (from legacy VM), (d) `migrate-to-aws.js --phase export-graph` (from legacy VM), (e) `migrate-to-aws.js --phase load-vectors` (from AWS EC2), (f) `migrate-to-aws.js --phase load-graph` (from AWS EC2), (g) `migrate-to-aws.js --phase verify` (from AWS EC2), (h) `verify-migration.js` for cross-environment parity check.

### Requirement 20: SageMaker Processing Jobs for Ingestion

**User Story:** As a developer, I want to run ingestion scripts as SageMaker Processing Jobs, so that I can offload compute-intensive embedding generation to on-demand instances without tying up the development EC2.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL provide a SageMaker job launcher script that submits any ingestion script as a SageMaker Processing Job.
2. THE job launcher SHALL accept parameters for instance type (e.g., `ml.g5.xlarge` for GPU, `ml.m5.large` for CPU-only), Model_Profile, backend target, and the ingestion script to run.
3. THE job launcher SHALL package the ingestion script, `ingestion_base.py`, `aws_backend.py`, the Embedding_Model_Registry, and all Python dependencies into a SageMaker-compatible container or processing input.
4. WHEN a SageMaker Processing Job completes, THE job launcher SHALL report the job status, document counts ingested, and any errors to stdout and optionally to S3.
5. THE SageMaker Processing Job SHALL have IAM permissions to access OpenSearch, Neptune, S3, Bedrock (for embedding generation), and Secrets Manager.

### Requirement 21: On-Demand GPU Scaling for Embedding Experimentation

**User Story:** As a researcher, I want to spin up GPU instances for embedding model experimentation and shut them down when done, so that I only pay for GPU compute when actively experimenting.

#### Acceptance Criteria

1. THE job launcher SHALL support GPU instance types (e.g., `ml.g5.xlarge`, `ml.g5.2xlarge`) for accelerated embedding generation with local models.
2. WHEN a GPU instance type is specified, THE embedding provider SHALL detect CUDA availability and use GPU acceleration for local model inference.
3. WHEN the SageMaker Processing Job completes or fails, THE instance SHALL be automatically terminated by SageMaker — no long-running GPU instances shall persist.
4. THE job launcher SHALL support a `--dry-run` flag that estimates job cost based on instance type, expected runtime, and current AWS pricing tier without submitting the job.

### Requirement 22: Production Re-Ingestion via SageMaker

**User Story:** As an operator, I want to trigger idempotent re-ingestion jobs from production when RAG quality degrades, so that the knowledge base can be refreshed without manual intervention on the development EC2.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL support triggering a full or partial re-ingestion as a SageMaker Processing Job from any environment with AWS credentials.
2. THE re-ingestion job SHALL use the same idempotent semantics defined in Requirement 7 (deterministic IDs, upsert/MERGE).
3. THE re-ingestion job SHALL accept a `--collections` argument to re-ingest specific content domains (e.g., `--collections code,docs`) rather than requiring a full re-ingest.
4. THE re-ingestion job SHALL write a completion report to S3 including before/after document counts, duration, and any errors.
5. THE re-ingestion job SHALL be triggerable via AWS CLI (`aws sagemaker create-processing-job`) or a convenience wrapper script.

### Requirement 23: SageMaker Job Container and Dependencies

**User Story:** As a developer, I want a pre-built container image for SageMaker ingestion jobs, so that job startup is fast and dependencies are consistent across runs.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL provide a Dockerfile for building a SageMaker-compatible container image with all ingestion dependencies (Python 3.11+, sentence-transformers, boto3, neo4j, chromadb, opensearch-py, fparser).
2. THE container image SHALL be published to Amazon ECR in the project's AWS account.
3. THE container image SHALL include the Embedding_Model_Registry and all ingestion scripts from `mcp_server_node/scripts/`.
4. WHEN a new ingestion script or dependency is added, THE container image SHALL be rebuildable via a single command (`docker build` or CDK asset).
5. THE container image SHALL support both CPU and GPU base images, selectable at build time via a build argument.

### Requirement 24: Amazon Nova Multimodal Embeddings Support

**User Story:** As a researcher, I want to generate embeddings using Amazon Nova Multimodal Embeddings, so that I can leverage configurable dimensions (256, 512, 1024, 3072) and explore whether a unified multimodal vector space improves retrieval for mixed content types like code, documentation, and diagrams.

#### Acceptance Criteria

1. THE Embedding_Model_Registry SHALL include Model_Profiles for Amazon Nova Multimodal Embeddings at each supported dimension: 256, 512, 1024, and 3072.
2. WHEN a Nova Multimodal Model_Profile is active, THE embedding provider SHALL invoke the Bedrock `nova-multimodal-embed-v1` model via `boto3`.
3. THE embedding provider SHALL pass the `outputEmbeddingLength` parameter to the Nova API to select the target dimension.
4. THE Ingestion_Pipeline SHALL support ingesting document images (architecture diagrams, workflow charts) alongside text content when using Nova Multimodal embeddings, placing both modalities in the same vector space.
5. THE Embedding_Model_Registry SHALL define Nova Multimodal profiles with short names following the pattern `nova{dim}` (e.g., `nova256`, `nova1024`, `nova3072`).

### Requirement 25: Matryoshka-Style Adaptive Dimension Retrieval

**User Story:** As a researcher, I want to store high-dimensional embeddings once and query at lower dimensions by truncation, so that I can trade off retrieval speed vs. accuracy without re-ingesting the entire corpus.

#### Acceptance Criteria

1. WHEN a Model_Profile supports Matryoshka-style truncation (e.g., Nova Multimodal at 3072-dim), THE Ingestion_Pipeline SHALL store the full-dimension embedding in the vector database.
2. THE Node_Adapter_Layer SHALL support a `--dimensions` query parameter that truncates stored embeddings to the specified prefix length at query time.
3. THE OpenSearch index mapping SHALL store the full-dimension embedding, and THE query SHALL use a script_score or k-NN query with the truncated prefix for lower-dimension searches.
4. THE Ingestion_Pipeline SHALL record in collection metadata whether the stored embeddings support Matryoshka truncation.

### Requirement 26: Hybrid Search — BM25 + Vector Fusion

**User Story:** As a developer, I want the MCP server to combine keyword search (BM25) with vector search and fuse the results, so that queries containing specific identifiers (function names, variable names, file paths) get precise matches while semantic queries still work well.

#### Acceptance Criteria

1. THE OpenSearch indices SHALL index the `content` field as both a `text` type (for BM25) and store the `embedding` field as `knn_vector` (for semantic search).
2. THE Node_Adapter_Layer SHALL support a hybrid search mode that executes both a BM25 query and a k-NN query in parallel and fuses results using Reciprocal Rank Fusion (RRF).
3. WHEN a query contains code identifiers (detected by camelCase, snake_case, dot notation, or file path patterns), THE Node_Adapter_Layer SHALL automatically boost the BM25 component weight.
4. THE hybrid search mode SHALL be configurable via a `search_mode` parameter: `vector` (default, backward compatible), `keyword` (BM25 only), or `hybrid` (fused).
5. THE OpenSearch search pipeline SHALL normalize scores from both retrievers before fusion.

### Requirement 27: Retrieval Quality Benchmarking Framework

**User Story:** As a researcher, I want an automated benchmarking framework that evaluates retrieval quality across different embedding models, dimensions, and search modes, so that I can make data-driven decisions about which configuration to deploy.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL include a benchmarking script that runs a fixed set of test queries against multiple Vector_Spaces and records precision@k, recall@k, MRR, and nDCG metrics.
2. THE benchmarking script SHALL accept a ground-truth file mapping queries to expected relevant documents (manually curated or derived from golden files).
3. THE benchmarking script SHALL output a comparison report (JSON + markdown) showing per-model, per-dimension, per-search-mode metrics side by side.
4. THE benchmarking script SHALL upload results to S3 with timestamps for longitudinal tracking of retrieval quality over time.
5. THE benchmarking script SHALL support running as a SageMaker Processing Job for consistency with the ingestion pipeline.

### Requirement 28: Graph-Augmented Vector Retrieval

**User Story:** As a developer, I want vector search results enriched with graph context from Neptune, so that when I search for a function, I also get its callers, callees, and module dependencies without a separate query.

#### Acceptance Criteria

1. THE Node_Adapter_Layer SHALL support a `graph_augmented` query mode that, after retrieving top-k vector results, expands each result with 1-hop graph neighbors from Neptune.
2. WHEN graph augmentation is enabled, THE Node_Adapter_Layer SHALL query Neptune for relationships (CALLS, USES, IMPORTS, CONTAINS) connected to each retrieved document's source entity.
3. THE graph-augmented results SHALL include the original vector search score plus a `graph_context` field containing neighbor nodes and relationship types.
4. THE graph augmentation SHALL be optional and backward compatible — existing queries without the flag SHALL behave identically to current behavior.
5. THE graph augmentation SHALL use a configurable hop depth (default: 1, max: 2) to control the breadth of context expansion.

### Requirement 29: Embedding Drift Detection

**User Story:** As an operator, I want to detect when the knowledge base embeddings have drifted from the current source content, so that I know when a re-ingestion is needed before RAG quality visibly degrades.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL include a drift detection script that samples N documents from each Vector_Space, re-embeds their source content with the current Model_Profile, and computes cosine similarity between the stored and fresh embeddings.
2. IF the mean cosine similarity for any collection drops below a configurable threshold (default: 0.95), THEN THE drift detection script SHALL report the collection as drifted and recommend re-ingestion.
3. THE drift detection script SHALL also check for stale documents whose source files have been modified or deleted since the last ingestion.
4. THE drift detection script SHALL output a drift report to S3 and optionally trigger a SageMaker re-ingestion job when drift exceeds the threshold.
5. THE drift detection script SHALL be schedulable as a CloudWatch Events rule (e.g., daily or weekly).

### Requirement 30: Domain-Adaptive Embedding Fine-Tuning Pipeline

**User Story:** As a researcher, I want to fine-tune embedding models on our domain-specific corpus (Fortran weather code, EE2 compliance, HPC workflow terminology), so that the embedding space learns to distinguish semantically similar but functionally different concepts in our domain.

#### Acceptance Criteria

1. THE Ingestion_Pipeline SHALL include a fine-tuning pipeline script that trains a domain-adapted embedding model using the Sentence Transformers v3+ `SentenceTransformerTrainer` with contrastive learning.
2. THE fine-tuning pipeline SHALL generate training pairs automatically from the existing knowledge base: positive pairs from same-section chunks, and hard negatives mined from high-similarity but different-section chunks within the same collection.
3. THE fine-tuning pipeline SHALL accept a base model parameter (e.g., `all-mpnet-base-v2`, `BAAI/bge-base-en-v1.5`) and produce a domain-adapted model saved to S3 and optionally registered in the Embedding_Model_Registry as a new Model_Profile.
4. THE fine-tuning pipeline SHALL run as a SageMaker Training Job with GPU instance support for accelerated training.
5. THE fine-tuning pipeline SHALL output training metrics (loss curve, validation MRR) and a before/after benchmark comparison using the Retrieval Quality Benchmarking Framework (Requirement 27).

### Requirement 31: Retrieval Feedback Loop for Continuous Improvement

**User Story:** As an operator, I want the system to learn from retrieval successes and failures over time, so that the embedding space continuously improves without manual curation of training data.

#### Acceptance Criteria

1. THE Node_Adapter_Layer SHALL log anonymized query-result pairs (query text, returned document IDs, result scores) to an S3 feedback log when queries are executed against the MCP tools.
2. THE feedback log SHALL capture implicit relevance signals: documents that appear in tool responses (positive signal) and documents that were retrieved but not used by the LLM (weak negative signal).
3. THE fine-tuning pipeline (Requirement 30) SHALL accept the feedback log as an additional training data source, using logged positive pairs and mined hard negatives to refine the embedding model.
4. THE feedback loop SHALL be opt-in and configurable — disabled by default, enabled via an environment variable or configuration flag.
5. THE feedback log SHALL NOT contain any personally identifiable information or raw user prompts — only the query text sent to the vector search and the document IDs returned.

### Requirement 32: Automated Hard Negative Mining from Graph Structure

**User Story:** As a researcher, I want to use the knowledge graph to generate high-quality hard negatives for embedding fine-tuning, so that the model learns to distinguish between structurally related but semantically different code entities.

#### Acceptance Criteria

1. THE fine-tuning pipeline SHALL mine hard negatives from the Neptune graph by finding pairs of entities that are structurally close (e.g., same module, same caller) but belong to different functional domains.
2. THE hard negative mining SHALL use graph distance as a difficulty signal: entities 1-hop apart in the graph but with different labels or different community assignments are strong hard negatives.
3. THE hard negative mining SHALL produce training triples (anchor, positive, hard negative) compatible with the Sentence Transformers `TripletLoss` or `MultipleNegativesRankingLoss`.
4. THE hard negative mining SHALL be runnable as a standalone script or as a preprocessing step within the fine-tuning pipeline.
