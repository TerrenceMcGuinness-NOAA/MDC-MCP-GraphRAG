REQUEST
-------

Please attach a new, single-statement inline policy to an existing IAM
role so that the AgentCore microVM can mount the just-deployed EFS
access point read-only at /mnt/workflow. No new IAM resources are
created. Existing inline policies on this role are not modified.


COMMAND TO RUN
--------------

    aws iam put-role-policy \
      --role-name mdc-mcp-rag-ecs-task-role \
      --policy-name efs-clientmount-workflow-ap \
      --policy-document '{
        "Version": "2012-10-17",
        "Statement": [
          {
            "Sid": "ClientMountWorkflowEFS",
            "Effect": "Allow",
            "Action": "elasticfilesystem:ClientMount",
            "Resource": "arn:aws:elasticfilesystem:us-east-1:903050880929:file-system/fs-032d52e4677000758",
            "Condition": {
              "ArnEquals": {
                "elasticfilesystem:AccessPointArn": "arn:aws:elasticfilesystem:us-east-1:903050880929:access-point/fsap-03e641f056b341f29"
              }
            }
          }
        ]
      }' \
      --region us-east-1

The verbatim JSON file in the repo is:

If preferred, the same call can use --policy-document file://...

WHY THIS IS NEEDED
------------------

The AgentCore microVM runs as
arn:aws:sts::903050880929:assumed-role/mdc-mcp-rag-ecs-task-role/...
and currently has Neptune, OpenSearch, ECR, logs, X-Ray, Secrets
Manager, SSM, and Bedrock InvokeModel permissions — but no
elasticfilesystem:ClientMount.

The workflow_info smoke probe (_smoke_workflow_info in
mcp_server_python/src/tools/smoke_queries.py) looks for a `jobs/`
directory beneath MCP_WORKFLOW_ROOT. Today the container has no
global-workflow checkout at any expected path, so the probe reports
the module unhealthy. The fix lands the global-workflow develop
worktree on a shared EFS volume, mounted read-only into the runtime
at /mnt/workflow/develop, with MCP_WORKFLOW_ROOT pointed at it.

Without elasticfilesystem:ClientMount on this role, the
update-agent-runtime call with --filesystem-configurations will
provision but the microVM mount attempt will fail with:

    mount.efs: failed to retrieve EFS DNS name ...
    NotAuthorized: ... is not authorized to perform:
    elasticfilesystem:ClientMount ...

so workflow_info would remain failing.

SECURITY SCOPE
--------------

Single statement. Single action. Single resource ARN. Single region.
Pinned to one access point via ArnEquals condition.

  Action:    elasticfilesystem:ClientMount  (one action — read-only)
  Resource:  fs-032d52e4677000758  (one file system ARN, us-east-1)
  Condition: AccessPointArn ArnEquals fsap-03e641f056b341f29
             (the role can mount via this AP and only this AP)
  Effect:    Allow

The role can already be assumed only by ecs-tasks.amazonaws.com and
bedrock-agentcore.amazonaws.com (per the existing trust policy). This
addition does not change who can assume the role, only what an
already-assumed session may do.

The access-point creationInfo (uid 1000, gid 1000, perms 0755) and
posixUser pin reads to the container's `app` user; the role has no
ClientWrite, so the mount is read-only end-to-end (in transit and at
the IAM layer).
