This maps directly to our updated CDK stack design. We have already

On the IAM front, I also want to highlight the excellent work your
admin team did in resolving our CloudFormation deployment blocker.
Rather than granting broad permissions to the CDK execution role, they
took the more secure approach of manually creating two scoped IAM
service roles:

  1. mdc-mcp-rag-ecs-task-role
     - Scoped to our specific Secrets Manager, SSM, Neptune, and
       OpenSearch resources only
     - No network or IAM modification permissions

  2. mdc-mcp-rag-ecs-execution-role
     - Standard ECS task execution policy for ECR image pulls and
       CloudWatch logging only

Our CDK stacks now import these pre-created roles rather than
attempting to create them through CloudFormation. This means
CloudFormation operates within the existing PowerUser constraints and
cannot create or modify IAM roles, VPC resources, or network
configurations. The admin team maintains full control over the
privilege boundary while we retain the ability to deploy our
application-layer resources (Neptune, OpenSearch, S3, ECS, Cognito,
WAF) through the standard CDK workflow.

We have verified this end-to-end with a dry run (cdk diff) and
confirmed that our deployment creates only the following resources:

  - Amazon Neptune cluster (graph database, private subnets)
  - Amazon OpenSearch domain (vector search, private subnets)
  - Amazon S3 bucket (data migration staging)
  - Amazon EFS filesystem (persistent storage)
  - AWS Secrets Manager entries (database credentials)
  - SSM Parameter Store entries (service endpoints)
  - Cognito User Pool (authentication)
  - WAF WebACL (rate limiting and common rule set)
  - ECS Security Group (HTTPS 443 + Neptune 8182 egress only)

No VPC, subnet, gateway, or IAM role resources are created by our
deployment. The security boundary is maintained.
