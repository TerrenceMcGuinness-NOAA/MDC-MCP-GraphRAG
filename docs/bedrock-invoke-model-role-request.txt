REQUEST
-------

Please attach a new, single-statement inline policy to an existing IAM
role so that the AgentCore microVM can invoke the Bedrock Titan Embed
Text V2 foundation model. No new resources are created. The existing
inline policy on this role is not modified.


COMMAND TO RUN
--------------

    aws iam put-role-policy \
      --role-name mdc-mcp-rag-ecs-task-role \
      --policy-name bedrock-invoke-titan-embed-v2 \
      --policy-document '{
        "Version": "2012-10-17",
        "Statement": [
          {
            "Sid": "bedrockInvokeModel",
            "Effect": "Allow",
            "Action": "bedrock:InvokeModel",
            "Resource": [
              "arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0"
            ]
          }
        ]
      }' \
      --region us-east-1


VERIFICATION
------------

    aws iam get-role-policy \
      --role-name mdc-mcp-rag-ecs-task-role \
      --policy-name bedrock-invoke-titan-embed-v2 \
      --region us-east-1

Expected: returns the policy document above with PolicyName
"bedrock-invoke-titan-embed-v2".

End-to-end verification (from the runtime, not the admin):

    # via the agentcore-kiro-proxy with a pinned collection
    search_documentation({"query": "test", "collection": "code-context"})

Expected: returns search results (HTTP 200) instead of
"AccessDeniedException: bedrock:InvokeModel".


WHY THIS IS NEEDED
------------------

The AgentCore microVM runs as
arn:aws:sts::903050880929:assumed-role/mdc-mcp-rag-ecs-task-role/...
and currently has Neptune, OpenSearch, ECR, logs, X-Ray,
secretsmanager, and ssm permissions — but no bedrock:InvokeModel.

Every BedrockProvider call inside the runtime fails with:

    AccessDeniedException: User:
    arn:aws:sts::903050880929:assumed-role/mdc-mcp-rag-ecs-task-role/...
    is not authorized to perform: bedrock:InvokeModel on resource:
    arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0
    because no identity-based policy allows the bedrock:InvokeModel action

This blocks the semantic search path: search_documentation calls that
land on titan1024 collections fail before any OpenSearch query is
issued. Without a pinned collection, multi_collection_query swallows
the per-collection EmbeddingError (return_exceptions=True) and reports
"No results found." Pinning a collection surfaces the verbatim error
above.

The same Bedrock call worked from a developer shell in Task 7.1 (p50
125 ms, p95 145 ms) because that path used developer IAM credentials,
not the runtime role.


WHY THIS REQUIRES ADMIN
